## Cypress Selectors and Assertions (Beginner-Friendly)

Selectors are how your test “finds” elements on the page. If your selector is wrong or unstable, your test becomes flaky (randomly failing). In UI automation, this skill is more important than writing long code.

You can think of it like this:
- In Java: you call a method on an object you already have.
- In Cypress: first you must **locate the element**, then you can **act** on it (click/type/assert).

---

## The 2 core selector tools you will use most

## 1) cy.get(selector) — CSS selector (most powerful)

`cy.get()` finds elements using **CSS selectors**. This is the default professional way.

### Common selector types

**By tag**
~~~js
cy.get("h1");
~~~

**By class**
~~~js
cy.get(".header");
~~~

**By id**
~~~js
cy.get("#Email");
~~~

**By attribute**
~~~js
cy.get('input[name="q"]');
~~~

**Nested (scope inside a container)**
~~~js
cy.get(".header").find("a");
~~~

### When to prefer cy.get()
- When you can target a stable attribute (best)
- When you need precise selection (unique element)
- When the text might change (language, UI text updates)

---

## 2) cy.contains(text) — visible text (fast and readable)

`cy.contains()` finds an element by its **visible text**. This is very beginner-friendly.

~~~js
cy.contains("Log in").click();
~~~

### When to prefer cy.contains()
- Buttons and links with stable text
- Quick navigation actions
- Assertions like “this text is visible”

---

## Combine cy.get() + cy.contains() (very important)

Sometimes the same text appears multiple times. Then `cy.contains()` alone may click the wrong element.

Solution: **scope** it.

~~~js
cy.get(".header").contains("Register").click();
~~~

This means:
- First locate the header
- Then find “Register” only inside the header

This is one of the most common “pro” patterns.

---

## Golden rules for stable selectors (read this like a checklist)

### 1) Best option: data attributes
If you control the app, always ask devs for attributes like:
- `data-cy`
- `data-test`

~~~js
cy.get('[data-cy="login-btn"]');
~~~

Why? Because these selectors are stable and meant for tests.

### 2) Acceptable options
- `id` (if unique and stable)
- `name` attribute for inputs
- simple stable classes

Examples from DemoWebShop:
~~~js
cy.get('input[name="q"]');         // search input
cy.get('input[value="Search"]');   // search button
cy.get('a[href="/login"]');        // login link
~~~

### 3) Avoid these (flaky selectors)
- `nth-child(...)`
- long CSS paths like `.a > .b > .c > ...`
- dynamic classes (generated by frameworks)
- text that changes often (marketing copy)

---

## Assertions (should) — how you validate UI behavior

Assertions confirm expected state. Cypress retries assertions automatically until they pass or timeout.

### Most common assertion types

**Visible**
~~~js
cy.get('input[name="q"]').should("be.visible");
~~~

**Exists**
~~~js
cy.get('a[href="/cart"]').should("exist");
~~~

**Contains text**
~~~js
cy.get(".page-title").should("contain", "Log in");
~~~

**Input has exact value**
~~~js
cy.get('input[name="q"]').type("laptop").should("have.value", "laptop");
~~~

### exist vs be.visible (important difference)
- `exist` means element is in the DOM (may be hidden)
- `be.visible` means it is actually visible to the user

---

## Why Cypress feels easier (auto-wait + retry)

Cypress automatically retries:
- `cy.get()` until the element appears
- `should()` until the assertion passes

So you usually do NOT need:
- `sleep()`
- manual waits
- `async/await` for Cypress commands

---

## Why this matters for testers

- Stable selectors = stable tests.
- Bad selectors are the #1 cause of flaky UI automation.
- Good scoping (get + contains) prevents clicking wrong elements.
- Correct assertions prevent false positives (tests that pass but shouldn’t).

---

## Common mistakes / gotchas

- Using `cy.contains("Text")` without scoping when the text exists in multiple places.
- Using overly specific selectors that break with small UI changes.
- Relying on `nth-child` because “it works right now”.
- Asserting too late or too early:
  - Make assertions close to the action you care about.
- Confusing `exist` and `be.visible`:
  - For user-facing checks, prefer `be.visible`.
